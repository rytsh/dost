# Single-submission notarization for Dost’s universal DMG and two architecture-specific app tarballs

Research date: 2026-10-23. Scope: read-only investigation of Apple documentation/forums, release-tool source, and the local workflow. No product code, jobs, releases, signing identities, or submissions were changed. **Recommendation: keep the existing final installer DMG intact, put it and the two separately signed thin app bundles in one temporary ZIP, submit once, prove coverage in the submission log, then staple the original DMG and all three original app bundles. Create the two release tarballs only after stapling.** The requested ZIP-containing-DMG-plus-two-ZIPs variant is supported by Apple’s general recursive-container contract, but the simpler ZIP-containing-DMG-plus-two-bare-app-directories avoids unnecessary archive layers. This is a documentation-backed design, not a workflow executed against Apple during this research.

## 1. What exactly does Apple promise about recursion, tickets, and multiple objects?

### Takeaway

Apple explicitly says it processes nested containers and generates tickets for nested objects, not only the submitted container. That is a sound basis for a single aggregate submission, but `Accepted` alone is not proof that each intended bundle was included or recognized: inspect ticket coverage and require successful stapling/validation of every distributed signed target. [Apple workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)

### Cited Findings

- **Authoritative recursive processing statement:** “The notary service accepts disk images (UDIF format), signed flat installer packages, and ZIP archives. It processes nested containers as well, like packages inside a disk image.” [Apple, Export a package for notarization](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Export-a-package-for-notarization)
- **Authoritative per-object ticket statement:** “The notary service generates a ticket for the top-level file that you specify, as well as for each nested file. For example, if you submit a disk image that contains a signed installer package with an app bundle inside, the notarization service generates tickets for the disk image, installer package, and app bundle.” [Apple, Upload your app to the notarization service](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Upload-your-app-to-the-notarization-service)
- **Authoritative multiple-item ZIP stapling statement:** “While you can notarize a ZIP archive, you can’t staple to it directly. Instead, run `stapler` against each item that you added to the archive. Then create a new ZIP file containing the stapled items for distribution. Although tickets are created for standalone binaries, it’s not currently possible to staple tickets to them.” [Apple, Staple the ticket to your distribution](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution)
- **Staple a bundle/container, not an arbitrary archive:** Apple says “To attach a ticket to your app, bundle, disk image, or flat installer package, use the `stapler` tool”, and explains that stapling permits ticket discovery without network access. This distinguishes notarized code identity from the transport archive; neither temporary ZIPs nor final tarballs are the objects to staple. [Apple, Staple the ticket to your distribution](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution)
- **Sign inside out; notarize only the outer container:** Apple DTS’s packaging guide says: “If you’re using nested containers, only notarize the outermost container.” Its example explicitly signs app, package, and disk image but submits only the disk image. It also says to sign nested containers that support signing. [Apple Developer Forums, Packaging Mac Software for Distribution, thread 701581](https://developer.apple.com/forums/thread/701581)
- **Check actual coverage:** Apple DTS says “The ticket covers the outermost container and everything within it”, and explicitly advises downloading the notarization log and checking “that the ticket does actually cover everything that you expect it to cover.” It also explains that when Gatekeeper checks an outer container, it ingests its ticket for later notarization checks. [Apple Developer Forums, thread 125512](https://developer.apple.com/forums/thread/125512)
- **Important caveat on that forum answer:** The same 2019 answer recommends against a multiple-item ZIP as the *distributed* outermost container. This is not a prohibition on using a temporary aggregate ZIP for submission, and current official docs explicitly say to staple “each item” added to a ZIP. Our aggregate ZIP is not delivered to users. The forum page was blocked by Apple’s browser-verification page during direct fetch; quoted text was available through indexed search, so treat it as corroboration, not the sole foundation. [Forum](https://developer.apple.com/forums/thread/125512); [current official docs](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution)
- **Always fetch the full log:** “Always check the log file, even if notarization succeeds, because it might contain warnings that you can fix prior to your next submission.” Apple provides `xcrun notarytool log <id> --keychain-profile <profile> developer_log.json`. [Apple, Check the status of your request](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Check-the-status-of-your-request)
- **Preserve the `.app` parent directory:** A developer reported successful notarization but missing app ticket coverage when `ditto` omitted `--keepParent`: the archive contained `Contents` rather than `myApplication.app`, and the ticket covered only the executable. This is developer-reported evidence, not a formal Apple guarantee. Apple’s own ZIP command uses `ditto -c -k --keepParent`. [Apple forum thread 133637](https://developer.apple.com/forums/thread/133637); [Apple ZIP instructions](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Export-a-package-for-notarization)
- **How the official text was read:** Apple’s documentation HTML is JavaScript-rendered; the exact documentation content above was fetched from Apple’s own JSON endpoint, which contains the full article and anchors. Its canonical current namespace is `Security`, not the older `Xcode` URL returned by older search results. [Apple documentation JSON](https://developer.apple.com/tutorials/data/documentation/security/customizing-the-notarization-workflow.json)

### Inferences

- **Final DMG + two app ZIPs inside temporary ZIP:** Yes, the general contract supports `submission.zip -> final.dmg -> universal.app`, plus `submission.zip -> arm64.zip -> Dost.app` and `submission.zip -> x86_64.zip -> Dost.app`. Generate the app ZIPs with `ditto --keepParent`. After acceptance, staple the original signed DMG and original three signed bundles, not the ZIPs. This is a direct application of Apple’s nested-container and each-item-stapling statements; no exact Apple sample showing this specific heterogeneous ZIP-of-ZIPs-and-DMG combination was found. [Apple recursion and tickets](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- **Prefer fewer layers:** A temporary ZIP holding the final signed DMG plus `arm64/Dost.app` and `x86_64/Dost.app` directly has the same intended coverage, less packing/unpacking, and no need to depend on inner-ZIP traversal for the thin apps. Preserve bundles as complete directories, not flattened contents or symlinks to originals. [Apple ZIP preparation and recursive tickets](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- **Notarizing only the existing universal DMG is insufficient evidence for the independently produced thin bundles.** Do not infer acceptance solely from matching bundle IDs, version numbers, source code, or even the presence of both CPU architectures inside another app. Include the exact thin bundles and verify each target. Some hashes can legitimately overlap, so the rule is not “every hash must differ”; it is “every required object/architecture must demonstrably be covered.” [Apple per-nested-object tickets](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Upload-your-app-to-the-notarization-service); [Apple DTS coverage check](https://developer.apple.com/forums/thread/125512)

### Gaps

- No paid/credentialed notarization submission or macOS runtime experiment was performed in this Linux research session. The specific aggregate layout must be proven once in CI via the downloaded `ticketContents`, all four staple/validate checks, and delivered-artifact verification.
- The docs give a general nested-container promise and a DMG/PKG/app example, not a comprehensive archive-type-by-depth support matrix. Do not silently extend it to tar.gz recursion, encrypted archives, unlimited nesting, symlink traversal, or hidden-file semantics.
- Ticket wording differs between the older forum’s singular aggregate “ticket” and the official docs’ per-file “tickets”. The relevant operational promise is coverage plus stapler support for each intended app/DMG, not an assumed one-ticket-per-archive implementation model.

## 2. What concrete one-submission ordering covers the DMG and all three bundles while preserving appearance?

### Takeaway

Build/sign all three app bundles first; create/sign the final universal installer exactly as today; submit that final DMG together with the exact two thin bundles in one temporary ZIP. After acceptance and coverage checks, staple the unchanged originals, then tar the thin bundles. Do not rebuild, re-sign, thin, or modify the installer’s filesystem after submission. This ordering follows Apple’s inside-out signing, recursive tickets, and post-acceptance stapling contract. [Apple](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow); [Apple packaging guide](https://developer.apple.com/forums/thread/701581)

### Cited Findings

- **Local context, direct file inspection:** `.github/workflows/ci.yml:132-151` builds a signed universal app/DMG, independently constructs thin apps using `make app APP=... MAC_TARGETS=...`, then invokes `scripts/notarize_macos.py`. The helper currently creates three submissions in parallel: `(DMG -> staple DMG + universal app)` and two `(ZIP -> staple thin app)` entries. It checks `Accepted` and validates stapled targets. These are local observations, not external claims. [Local workflow](../../.github/workflows/ci.yml); [local helper](../../scripts/notarize_macos.py)
- **Local packaging already has the right final ordering:** `.github/workflows/ci.yml:153-170` creates architecture-specific `.tar.gz` files only after notarization/stapling, extracts them, and checks signature, architecture, stapled ticket, and Gatekeeper assessment. Keep those guards. [Local workflow](../../.github/workflows/ci.yml)
- **Local installer appearance:** `Makefile:128-141` uses `create-dmg` with a background, fixed window geometry, one visible `Dost.app`, and an Applications shortcut. The final DMG is then signed. Aggregating that completed file outside the DMG leaves its installer contents/layout untouched. [Local Makefile](../../Makefile)
- **Apple’s packing guidance** recommends `ditto` instead of `cp` when assembling a disk-image staging directory because `ditto` preserves symlinks. It recommends a signed read-only UDIF `UDZO` image when using third-party layout tools. [Apple packaging guide](https://developer.apple.com/forums/thread/701581)
- **Apple’s two-round exception concerns custom executable/network installers**, not a normal drag-to-Applications DMG: “If you distribute your software via a custom third-party installer, you need two rounds of notarization.” For a network installer, separately notarize the installer and downloaded items. Our one-submission proposal explicitly includes both initial-install and update payloads; it is not an excuse to notarize only the installer and omit downloads. [Apple Important note](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Export-a-package-for-notarization)

### Inferences

#### Recommended submission contents

```text
submission.zip                  # temporary; never a release asset
  submission/
    Dost-<version>.dmg           # exact final signed installer file
      [mounted contents]
        Dost.app                # signed universal bundle, both architectures
        Applications -> /Applications
        existing background/layout files
    arm64/
      Dost.app                  # exact independently signed thin bundle
    x86_64/
      Dost.app                  # exact independently signed thin bundle
```

The universal app need not be duplicated outside the DMG because Apple recursively scans the DMG; retaining the original `target/Dost.app` provides a writable identical bundle to staple afterward. The key equality is signed identity/content between that original and the DMG copy, not filesystem path. Verify rather than assume this equality. [Apple recursive tickets](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Upload-your-app-to-the-notarization-service)

#### Concrete ordering (design for a future implementation, not executed here)

1. Build the universal executable and both thin executables. Finish all bundle resources, metadata, entitlements, and signing before submitting. Keep thin bundles independent; do not derive a release thin app by thinning an already notarized/signed universal bundle. Freeze the three bundle inputs. [Apple inside-out signing](https://developer.apple.com/forums/thread/701581); [local existing guard](../../.github/workflows/ci.yml)
2. Build the **final** installer with the existing `create-dmg` appearance using the universal app; sign the completed DMG with Developer ID Application and a timestamp. `hdiutil verify` and signature verification should pass before submission. Record signed identity/CDHashes of apps per architecture and the DMG. Mount the DMG read-only and verify its app matches the intended universal bundle. [Apple packaging](https://developer.apple.com/forums/thread/701581); [Apple integrity advice](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Avoid-long-notarization-response-times-and-size-limits)
3. Create a fresh per-run staging directory **outside all app bundles and outside the final DMG**. Copy the final DMG as a regular file; use `ditto` to copy each thin bundle to separate architecture directories, retaining each `Dost.app` parent. No symlinks to build-output apps. Archive the staging directory with `ditto -c -k --keepParent`. [Apple ditto example](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Export-a-package-for-notarization)
4. Submit **only this ZIP**, once: `xcrun notarytool submit <submission.zip> --keychain-profile <profile> --wait --output-format json`. Persist the submission UUID and response. Require `status == Accepted`; a zero process exit or a successful upload is not the release gate. [Apple status workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Check-the-status-of-your-request); [electron implementation](https://github.com/electron/notarize/blob/main/src/notarytool.ts)
5. Fetch `notarytool log <UUID> ... <log.json>` even for success. Check `ticketContents` against an expected manifest of object identity + architecture + nested path: the DMG itself; universal app bundle for arm64 and x86_64; arm64 thin app bundle; x86_64 thin app bundle; and their expected code contents. Do not count only raw entries: app/executable entries and duplicate hashes can coexist. Normalize observed paths instead of guessing every ZIP/DMG prefix in advance. Reject missing app-bundle coverage even if its inner executable is listed. [Apple log advice](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Check-the-status-of-your-request); [Apple DTS check coverage](https://developer.apple.com/forums/thread/125512); [missing-bundle pitfall](https://developer.apple.com/forums/thread/133637)
6. Staple and validate **four originals**: the final DMG, `target/Dost.app`, `target/macos/arm64/Dost.app`, and `target/macos/x86_64/Dost.app`. Use bounded retry/backoff for transient ticket-fetch failures, never a new submission simply because stapling has not propagated. Any persistent failure blocks packaging/publishing. `electron/notarize` provides precedent for three stapling retries. [Apple staple each item](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution); [electron retry implementation](https://github.com/electron/notarize/blob/main/src/index.ts)
7. Verify all three originals still pass strict code-signature checks. For the final DMG, assess with `spctl --assess --type open --context context:primary-signature -v <dmg>`; for apps use execute assessment. **Do not rebuild/re-sign the DMG to insert the newly stapled universal app.** Its embedded app is notarized through the submitted DMG, while the outer stapled DMG supplies the install-distribution ticket; the separately stapled original universal app is not retroactively inside that image. [Apple DTS Gatekeeper ticket ingestion](https://developer.apple.com/forums/thread/125512); [local existing DMG assessment command](../../Makefile)
8. Create final thin app tarballs from the now-stapled originals. Extract each tarball using the same semantics as the updater, then require valid signature, exact architecture, and `stapler validate` on the extracted app; preserve existing workflow checks. Compute release checksums **after** stapling/packing. The tar.gz itself gets no stapler operation. [Apple supported stapling objects](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution); [local verification](../../.github/workflows/ci.yml)
9. Integration-test the *downloaded/quarantined* installer and both update paths on clean macOS systems, including offline installation/launch after download. A CI `spctl` success with online/cached tickets is not an offline fresh-machine test. [Apple offline motivation](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Staple-the-ticket-to-your-distribution)

#### Alternatives and traps

| Approach | Covers final DMG and all three apps in one submission? | Appearance / tradeoff |
|---|---|---|
| Final signed DMG + two bare thin apps in temporary ZIP | Documentation-backed yes, subject to explicit coverage/stapling gates | **Preferred:** existing installer unchanged; fewer layers |
| Final signed DMG + two thin app ZIPs in temporary ZIP | General recursive-container contract supports it; exact combination not experimentally verified here | Installer unchanged; unnecessary nested compression |
| Final DMG contains universal app plus thin apps in `arm64/` and `x86_64/`; submit that final DMG | Yes under Apple’s DMG recursive/object ticket contract | Larger delivered installer; extra directories/apps. Hiding extras does not remove their size or need for testing |
| Temporary outer DMG contains final installer DMG and two thin apps | Same general recursive-container basis | Final installer unchanged, but building/mounting another DMG adds machinery compared with ZIP |
| Temporary DMG contains all three apps, but **not** final installer DMG; then build final DMG after acceptance | Apps covered; **final DMG not covered** by that submission | Cannot staple a newly created final DMG merely because the apps are notarized |
| Submit three apps in ZIP, staple them, then create final DMG | Apps covered; **final DMG not covered** | This is similar to some tools’ default behavior; does not meet this assignment’s stronger requirement |
| Put thin apps in final DMG for scanning, then remove them/rebuild DMG after acceptance | Submitted DMG covered; new modified/rebuilt DMG not established as covered | **Reject** if requiring a ticket for the final DMG |
| Submit current universal-only DMG and later staple independently signed thin apps without including them | No demonstrated coverage of thin apps | **Reject**: not a robust assumption |

The table’s coverage conclusions are applications of the nested-object ticket contract, not claims that each exact layout has been independently tested. [Apple ticket contract](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Upload-your-app-to-the-notarization-service)

### Gaps

- **If the requirement becomes “a physically stapled universal app must be embedded inside the final physically stapled DMG,” this simple one-submission design does not provide that.** Standard inside-out manufacturing would notarize/staple the app, build/sign the DMG containing it, then notarize/staple that final DMG: normally two rounds. Do not claim the current original-app staple changes the app already inside a read-only DMG. No supported one-pass in-place DMG-rewrite technique preserving its notarization identity was established.
- No guarantee was found that one larger submission completes faster than three concurrently submitted smaller ones. It reduces submission count (three to one) and orchestration, not necessarily wall-clock scan time. Apple recommends minimizing file count, avoiding heavily compressed disk images, and limiting notarizations to 75 per day, but does not promise a batching speedup. [Apple performance guidance](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow#Avoid-long-notarization-response-times-and-size-limits)
- Exact tar metadata behavior must be checked against Dost’s actual updater extraction, not inferred solely from the fact that tar.gz can carry a bundle. Preserve the existing extraction validation; offline end-to-end tests remain necessary.

## 3. What do established release tools actually do, and what does that prove?

### Takeaway

Established tools provide useful precedents for outer-DMG notarization or app-ZIP notarization followed by stapling and packaging, but the inspected code does **not** demonstrate this exact multi-artifact aggregate submission. Critically, app-only notarization followed by DMG creation does not satisfy the stricter requirement that the final DMG itself have a ticket. [GoReleaser native flow](https://goreleaser.com/customization/sign/notarize/#native-1); [Tauri DMG source](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/dmg/mod.rs)

### Cited Findings

- **GoReleaser native notarization documents the right outer-container order:** its published graph is `Create Binaries -> Create App Bundles -> Sign App Bundles -> Create DMGs -> Notarize DMGs`; it says “Once the App Bundle is signed, it needs to be packaged in a DMG. Finally, the DMG is notarized and used from that point on.” It documents native support since v2.8, as a Pro feature. This validates the concept of notarizing the completed DMG, not a need to submit each inner app separately. It does **not** demonstrate one aggregate ZIP or prove thin app coverage when those bundles are absent. The native Pro implementation was not publicly available in the inspected OSS source, so this is authoritative tool documentation rather than a claim of complete source audit. [GoReleaser docs, updated 2026-08-13](https://goreleaser.com/customization/sign/notarize/)
- **Do not confuse GoReleaser’s “single run” with a single Apple submission:** its cross-platform section says the notary step does everything “in a single run” but that statement is about the tool stage, not a documented aggregate upload. It also explicitly warns that putting only a signed/notarized executable inside a non-notarized `.app` is not sufficient. [GoReleaser docs](https://goreleaser.com/customization/sign/notarize/)
- **Electron’s maintained notarization library:** `src/notarytool.ts` special-cases `.dmg` and `.pkg` for direct upload; otherwise it builds a temporary ZIP with `ditto -c -k --sequesterRsrc --keepParent`, runs `notarytool submit --wait --output-format json`, fetches logs when an ID is returned, and accepts success only if the process succeeded **and** status is `Accepted`. [electron/notarize source](https://github.com/electron/notarize/blob/main/src/notarytool.ts)
- **Electron staples the original target after successful submission:** `src/index.ts` checks signatures, awaits `notarizeAndWaitForNotaryTool`, then calls `stapleApp({ appPath })` with three retries. It does not need to replace the original app with an extracted copy from the submission ZIP. This is useful direct implementation evidence for stapling originals corresponding to submitted copies. [electron/notarize source](https://github.com/electron/notarize/blob/main/src/index.ts)
- **electron-builder calls app-level notarization during signing:** its `MacPackager.sign()` invokes `helper.notarizeIfProvided(appPath)` for non-MAS builds; packaging into distributable targets happens after packing/signing. This supports app-first workflows, not a proof that every final DMG is notarized. [electron-builder MacPackager source](https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/macPackager.ts)
- **Tauri source clearly separates app notarization from DMG construction:** `app.rs::bundle_project()` signs the app and calls `notarize(...)` or `notarize_without_stapling(...)` before returning. `dmg/mod.rs::bundle_project()` then makes the image and signs it; its inspected body contains no final `notarytool`/notarize call. Therefore do not cite “Tauri notarizes DMGs” as evidence that app notarization magically covers subsequently created containers. [Tauri app source](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs); [Tauri DMG source](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/dmg/mod.rs); [Tauri sign wrapper](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/sign.rs)
- **cargo-packager source has the same distinction:** `codesign/macos.rs::notarize()` creates a temporary ZIP of `app_bundle_path` with `--keepParent --sequesterRsrc`, submits it, checks `Accepted`, then staples the original app path. Its `package/dmg/mod.rs` creates and optionally signs the DMG, but contains no final DMG notarization call. The source even includes an attempt/comment to “sign the zip file”; Apple explicitly says ZIPs cannot be signed, so do not blindly copy every implementation detail from third-party code. [cargo-packager notarization](https://github.com/crabnebula-dev/cargo-packager/blob/main/crates/packager/src/codesign/macos.rs); [cargo-packager DMG packaging](https://github.com/crabnebula-dev/cargo-packager/blob/main/crates/packager/src/package/dmg/mod.rs); [Apple ZIP limitation](https://developer.apple.com/forums/thread/701581)
- **A particularly useful corrected discussion:** cargo-packager issue #395 initially claimed DMG notarization was required to fix layout. The author later withdrew the reproduction, reporting a system-wide issue, and observed that Tauri did not notarize DMG files either. The maintainer explicitly corrected their prior assertion: “yeah, idk what i was looking at.” This is evidence **against** trusting the first reply or issue title as an implementation fact; inspect final comments/source. It does not establish that layout corruption is a notarization symptom. [Full issue #395, 2025-11-27](https://github.com/crabnebula-dev/cargo-packager/issues/395)

### Inferences

- The strongest foundation for an aggregate one-submission workflow is **Apple’s explicit recursion and per-nested-object ticket documentation**, not a claim that electron-builder/Tauri/GoReleaser already implement the exact arrangement. Keep implementation conclusions narrow: packaging stage, submitted object, accepted-status gate, original-target stapling, and retries. [Apple](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow); [electron implementation](https://github.com/electron/notarize/blob/main/src/notarytool.ts)
- Dost’s present helper already has the correct high-level separation between submitted artifacts and stapling targets. A future change could replace its three submission entries with one aggregate artifact whose target list is `[final_dmg, original_universal_app, arm64_app, x86_64_app]`, while retaining fail-closed acceptance and adding full-log/coverage verification. That is a design inference from the local source, **not a code change made during this task**. [Local helper](../../scripts/notarize_macos.py)

### Gaps

- No inspected established-tool implementation supplied a tested exact `ZIP(DMG(universal.app), ZIP(arm64.app), ZIP(x86_64.app))` example. The capability is documentation-backed; the exact concrete composition still needs its first controlled validation.
- Repository source URLs above use moving `main`, `master`, or `dev` branches as fetched on the research date. They are precise file URLs, not immutable commit permalinks; future readers should pin a commit before using them as permanent implementation evidence.
- Tauri’s current wrapper delegates to `tauri_macos_sign`; its internal notarization implementation was not fully inspected. The cited conclusion is restricted to the explicit app and DMG call sites fetched here.
